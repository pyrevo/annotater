### Added
- All three bundled sample datasets are now reachable from the React interface. The sample selector is populated from `GET /api/sample-datasets`, so the ids, names and declared operations have exactly one source (the server's catalog) and the frontend no longer hard-codes one of them. Loading a sample also applies the operation the catalog declares for it, so the closest-proximity sample is run as a closest search.
- `GET /api/meta` publishes `max_file_size_mb`, the per-file upload limit the server actually enforces. The React upload hints render that value instead of a number of their own, so the interface and the enforced limit cannot drift apart.
- A regression suite for the RC4 polish findings (`frontend/src/rc4_polish.behavior.test.jsx`) and a backend contract suite for the upload limit, the manual pages and the frontend wording (`tests/test_rc4_polish_contract.py`). Deterministic Vitest and real-browser regressions cover the non-JSON HTTP refusal and the sample-declared operation (`frontend/src/rc4_final.behavior.test.jsx`, `tests/test_browser_multi_tab.py`).
- Two real-browser regressions: a replaced dataset never leaves a stale result on screen or in an export, and a refused upload can be retried with the very same file.
- Modern React + Tailwind CSS frontend interface with real-time progress indicators, interactive statistics visualizations, gene frequency charting, and one-click data previews.
- FastAPI backend service (`streamlit_app.api_server`) exposing annotation endpoints, sample dataset inspection, and progress tracking.
- Automated frontend linting and build validation step (`oxlint` + `vite build`) in GitHub Actions CI workflow (`python-tests.yml`).
- A stable `ci-gate` GitHub Actions aggregate status check that requires every essential validation job (lock consistency, Ubuntu and macOS pytest, frontend lint/build, real-browser regression, and Docker smoke) to succeed; a failure, cancellation, skip or missing result in any required job fails the gate closed.
- Multi-stage Docker build producing an optimized production container image with embedded frontend assets and non-root user execution (`appuser:appgroup`).
- Restored the "Charts and gene list" results panel from the original Streamlit application: a top-10 gene/feature bar chart and gene-list export (`.txt` / comma-separated `.csv`) for external enrichment tools (g:Profiler, Enrichr, DAVID, STRING), served by the new `GET /api/results/gene-list` endpoint and the `gene_list` field of the execute response.
- `POST /api/dataset/clear` endpoint that discards one role's stored dataset together with any result derived from it, without allocating a session (it is a state removal, not a write).
- Frontend behavioral test suite (dev-only `vitest` + `jsdom` + Testing Library, `frontend/src/app.behavior.test.jsx`, run by `npm test`) covering the two final-gate races in the real component: coordinate-system change invalidating a loaded dataset (N2), and a superseded in-flight `/api/execute` response being discarded while all inputs stay locked (N3).
- Session-scoped custom chromosome registries over HTTP: `POST /api/registry` uploads and validates a custom mapping, `GET /api/registry` returns the session's mapping metadata (never its content) and `DELETE /api/registry` removes it for a named revision. The mapping is validated structurally and never repaired, is admitted against the M2.2a resource budget, is never persisted and never shared between sessions. The endpoint contract is documented in `docs/technical/registry-api.md`.
- `POST /api/execute` accepts an optional `registry_rev`, which binds a run to the session's custom chromosome mapping: the run needs the named revision to be the current one, leases the mapping while it runs and checks its identity again before the result is stored. A run uses exactly one chromosome source — the custom mapping, a bundled assembly, or none when the names are kept as provided — and naming both a custom mapping and an assembly is refused.
- The execute response and the stored result carry the run's chromosome provenance (`registry`): the custom mapping's revision, content digest, display name and sequence count; the canonical assembly id of a bundled run; or nothing at all for a run that kept the names as provided.

### Changed
- The documentation site is now built with Zensical (Classic variant, pinned to 0.0.73) instead of Material for MkDocs, and published through the same GitHub Pages deployment, which now deploys only for pushes to `main` (tag pushes build and verify but no longer deploy). Page paths, directory-style URLs, navigation, canonical URLs and content are unchanged; the site is verified against a Material reference build and in a real browser (including search) before it is uploaded. Intentional differences and the rollback procedure are in `docs/implementation-notes.md`.
- Repository documentation now describes the React/FastAPI application as the current generation and the `0.1.0-rc4` image as planned and unpublished, while keeping `0.1.0-rc3` as the latest published pre-release. Local instructions use port 8000 and `/health`; the legacy Streamlit instructions remain for the published RC1–RC3 images. The Serve guide records the documented 100 MB other/custom app upload limit without asserting whether it is per file or per request, treats `MAX_FILE_SIZE_MB=100` as a recommended validation setting, and keeps one replica because sessions are in memory.
- The React genome-assembly selector no longer calls its no-assembly option "Auto-detect": AnnotateR never detects or guesses an assembly, and the option now states what it does — "No assembly (keep chromosome names as provided)". Choosing a chromosome naming without a bundled assembly or a custom mapping now disables the Run button and explains why, instead of failing at run time with `assembly_required`. The backend check is unchanged and still refuses the same combination.
- The results panel now states that the table is a preview of the first 100 rows, that the downloaded CSV, TSV, Excel and VCF files contain the complete result, and that the display filter applies to the preview while an export applies the same filter to the complete result. The preview itself is unchanged.
- The manual pages now state the upload limit the current React/FastAPI application enforces (`MAX_FILE_SIZE_MB`, 500 MB by default) instead of Streamlit's 200 MB default, which belongs to the older Streamlit generation and is preserved as such in `docs/deployment.md`. The enforced limit is unchanged.
- The intentional difference between a dataset *replacement* and a dataset *clear* is now documented: a clear drops the result derived from the cleared revision, a replacement keeps it (the result belongs to the run that produced it), and the interface withdraws its own displayed result on every invalidating event, so an old result is never shown or exported as if it belonged to a newly uploaded dataset.
- A custom chromosome mapping is now a first-class session resource of the FastAPI backend: replacing or clearing it invalidates every result derived from the previous content (SPEC §5.1.1 item 9), while a result derived from a bundled assembly or from keeping the names as provided is left alone. The invalidation compares the stored result against the session's current committed revision under the session lock, so a delayed cleanup from an earlier write cannot delete a result produced with a newer registry. The registry lifecycle gained three additive primitives: an atomic revision-scoped clear (`clear_for_revision`), a read-only identity accessor (`current_metadata`) and commit-time session materialisation (`register(..., materialize=...)`); the existing lifecycle behaviour is unchanged.
- An anonymous `POST /api/registry` now materialises its session only at the successful commit. Invalid mappings, 413/429 refusals, superseded writes and cancelled parses allocate no session, issue no cookie and can no longer evict a live session from a full store; a successful write creates exactly one session. A failed registry upload from an existing session leaves that session, its datasets and its committed mapping untouched.
- Result statistics report match coverage as query-row-identity matches (`matched_query_count`), and the React results header and summary use it instead of result-row counts.
- Annotated VCF export is only offered for VCF queries, in the React UI and enforced at the HTTP boundary, matching the Streamlit application.
- The results table is cleared whenever the dataset or any execution configuration changes, so a stale result can no longer be displayed as if it belonged to a new run.
- Single-position queries (no end column) now map to one-base intervals via an explicit "None (single positions)" end-column sentinel instead of silently using a positional column.
- Changing the declared coordinate system of an already-loaded file now invalidates that side's dataset (locally, server-side, and the file picker) and requires a re-upload under the new declaration, instead of silently re-running the stale, already-normalized table (final-gate finding N2).
- The coordinate-system selectors, file pickers, column-mapping controls, sample loader and run button are locked while an upload or column mapping is in flight, and each side (query/annotation, tracked independently) carries a dataset generation: an upload or mapping response parsed under a superseded declaration is discarded and its possibly-stored server copy cleared, so it can no longer silently (re)populate a side with off-by-one coordinates. An upload or mapping that fails with a network error now drops that side on both client and server, since the server outcome is unknown (final-gate finding N2-R). Server-side, `POST /api/apply-mapping` now commits only if the stored query is still the table it read: a clear or re-upload that lands while the mapping runs yields HTTP 409 instead of a 500 (`KeyError`) or a silent overwrite of the newly uploaded table with the superseded one. Behavioral tests cover first upload, re-upload/slow parse, mapping, failures, and the annotation-side declaration (N7).
- While an annotation run is in flight all configuration controls are locked, and a superseded run's response can no longer land in the UI: an `/api/execute` response is applied only if no invalidating event happened after the run started (final-gate finding N3). The results header now states the operation mode and join the run actually used.
- `docs/deployment.md` now states what the React/FastAPI image actually reads: `PORT`, `FORWARDED_ALLOW_IPS`, `MAX_FILE_SIZE_MB`, and the new `ANNOTATER_CORS_ORIGINS`; the upload's temporary parsing copy lives under the system temp directory (`tempfile.mkdtemp`) and is deleted immediately, not under `TEMP_DIR` (which, with `CLEANUP_AFTER_HOURS`, belongs to the Streamlit-generation helpers only); the session-cookie section documents the `__Host-` prefixed HTTPS cookie name (final-gate finding N5).

- Tabs of one browser share one server session; each stored dataset and result now carries an opaque server-issued revision. `POST /api/execute` requires `query_rev`/`annot_rev`, `POST /api/apply-mapping` requires `query_rev`, and `GET /api/results/data`, `/api/results/gene-list` and `/api/export/{fmt}` require `result_rev` (returned as `revision` / `result_revision` by upload, load-sample, mapping and execute). A missing revision is refused with 428 and a stale one with 409 `revision_conflict`, never answered with another tab's datasets or result; execute and mapping commit only if their datasets were not replaced while they ran. The React UI sends these revisions, fetches exports with the displayed result revision, and shows "Changed in another tab" on a conflict instead of silently running on or exporting another tab's analysis (release-gate finding F1).

### Fixed
- An HTTP upload refusal whose body is not JSON (a reverse-proxy HTML page, plain text, an empty body or malformed JSON) is now handled as a known refusal instead of an unknown-outcome network error (#82). The previously loaded dataset, its revision and the coordinate declaration survive, no `POST /api/dataset/clear` is sent, no raw error page is displayed, and the same file remains retryable. A genuinely unanswered request still follows the revision-safe unknown-outcome recovery path, and `409 revision_conflict` handling is unchanged. `POST /api/load-sample` uses the same defensive body handling.
- Loading a bundled sample now applies the operation its catalog entry declares even when `GET /api/meta` is unavailable (#83), using the interface's own operation list as the fallback instead of the previously selected operation. An absent or unsupported declared operation blocks the run with a recovery message rather than silently running the sample under an unrelated operation; the block persists while either sample side remains loaded and clears only when both sample sides are replaced or the user explicitly chooses an operation. A loaded metadata response without a modes list fails closed instead of assuming support. Sample coordinate provenance, the generation guards and the scientific API contract are unchanged.
- A refused upload can now be retried with the very same file. A native file input keeps its previous selection and fires no change event for an identical selection, so after a refusal the user's second attempt silently did nothing: the interface repeated the error without sending a request. The picker is now remounted after a refusal, exactly as the coordinate-declaration invalidation already does; the previously loaded dataset still survives the refusal.
- A named clear of an already-empty dataset side is a 200 no-op that now commits nothing: it no longer advances that side's write-order high-water mark, so it cannot supersede an earlier in-flight upload with a spurious `409 revision_conflict`. A matching clear of a loaded side still advances the mark, and stale or revision-less clears are still refused without committing (#64).
- Loading a bundled sample now shows the coordinate convention actually applied to the loaded files as read-only provenance on each sample card, instead of leaving the UI silent about it (#54). Each sample declares an explicit authoritative source system per side (BED 0-based, GFF3/VCF 1-based); `POST /api/load-sample` reports the system it applied and `GET /api/sample-datasets` exposes the declarations. Crucially, the sample load does **not** rewrite the coordinate selectors — those are the user's declaration for *future* uploads, so they keep Auto-detect (or an explicit user choice) and an extension-neutral file uploaded afterwards is still sniffed, not silently reinterpreted (independent-review finding F1: on an earlier revision, loading the 1-based-annotation `gene_overlap` sample made the next BED-like `.tsv` annotation parse as 1-based, shifting `[100, 200)` to `[99, 200)`). Query and annotation stay independent, an explicit declaration change after a load still fires the N2 invalidation/re-upload contract, superseded or 409 sample responses cannot install sample-derived state, and normalization, execution and the meaning of Auto-detect are unchanged (`tests/test_sample_coordinate_consistency.py`, `frontend/src/app.behavior.test.jsx`, `tests/test_browser_multi_tab.py`).
- `POST /api/apply-mapping` now participates in the same per-`(session, query)` arrival-order write contract as upload, sample load and clear (#60): it reserves a write stamp before the (possibly slow) column mapping, refuses to commit when a later-started write to `query` has already committed, records its stamp only on success, and advances the query side's committed high-water mark. An upload that arrived before a mapping but finished parsing after it committed is now refused with `409 revision_conflict` instead of silently overwriting the mapped table (`tests/test_mapping_write_order.py`). Query and annotation ordering stay independent; a failed or superseded mapping records nothing and does not advance the mark.
- `POST /api/dataset/clear` now follows the same revision contract as every other state-changing endpoint: a clear that names no revision while a dataset is stored is refused with 428 instead of silently discarding whatever is stored, and a rejected clear (409/428) commits nothing and does not advance the write-order high-water mark. Clearing a dataset now discards only a result bound to the cleared revision, leaving a result derived from any other revision alone (#51, #52). The React UI never sends a revision-less clear: on an unknown-outcome network error it clears only the last revision the tab owned (or nothing, when it owned none), a superseded successful response clears only the revision it reported, and a superseded failure sends no clear. An opt-in real-browser test proves one tab's clean-up cannot wipe a newer dataset another tab of the same session stored.
- Single-position (end-column-less) queries no longer depend on which column happens to be third in the input table.
- `POST /api/upload` no longer parses on the event loop: format detection, parsing and normalization now run in a worker thread (`anyio.to_thread.run_sync`), so a large upload can no longer freeze the single Uvicorn worker's loop and stall every other session's request and the `GET /health` readiness probe for the duration of the parse (#55). The upload's session commit remains a single locked critical section, so a concurrent clear or replacement still cannot expose a dataset and revision that do not match.
- Parsing now borrows from a limiter dedicated to uploads (default 2 concurrent, `ANNOTATER_MAX_CONCURRENT_PARSES`) instead of AnyIO's shared default threadpool, so a burst of uploads can no longer exhaust the pool that synchronous endpoints such as `GET /health` run on and starve them (#55). Waiting uploads await a token on the event loop and never block it.
- Same-session writes are ordered by request arrival: if an upload or sample load is superseded by a newer upload, sample load or clear that commits while the older request is still parsing, the older request is refused with `409 revision_conflict` and stores nothing, instead of silently overwriting the newer dataset — even across tabs of one browser session (#55). Clears carry the same ordering, so an in-flight upload cannot resurrect a side that was just cleared.
- A `409 revision_conflict` on an upload or sample load now drops the superseded side(s) in the React UI, clears dependent results and shows the "Changed in another tab" warning with Run disabled, instead of leaving the tab's previous dataset displayed as loaded with Run enabled (#58). Sample loading now carries the same per-side request-generation guard as uploads, so a stale sample-load response (success or conflict) can no longer overwrite a newer dataset. Behavioral tests cover both sides, sample loading, the stale-response case and the success paths; an opt-in real-browser test drives the recovery path in Chrome.

### Security
- `GET /api/results/data` page size is bounded to 10,000 rows per request.
- Unauthenticated read requests are served by throwaway sessions: they consume no session capacity, receive no session cookie, and can no longer evict a real user's state from the bounded session store.
- Session capacity is now consumed lazily on the first state write: anonymous or forged-cookie requests — including failed writes such as oversized or invalid uploads — allocate no session slot and can no longer exhaust the store or evict a real user's session (final-gate finding N4).
- Over HTTPS the session cookie is issued and honoured only under the `__Host-` prefixed name `__Host-annotater_session` (Secure, `Path=/`, no `Domain`), scoped to the exact issuing host: an unprefixed `annotater_session` cookie — even one carrying a live token planted by a sibling subdomain — is ignored over TLS, closing the session-fixation path (final-gate finding N1). Plain-HTTP local development keeps the unprefixed name.
- The session cookie is now read byte-exactly from the raw `Cookie` header instead of Starlette's parsed cookies, which strip Unicode whitespace from names: a sibling-settable `\xa0__Host-annotater_session` (or `\x85…`) cookie was being honoured as the `__Host-` cookie and could fixate a victim's session and expose their data. A cookie name that is not the byte-exact `__Host-annotater_session` (or, over plain HTTP, `annotater_session`) is ignored; only the byte-exact session cookie presented more than once is rejected with HTTP 400 as genuinely ambiguous (final-gate finding N1-R).
- Alias cookie names that AnnotateR can never issue are ignored rather than rejected: the previous fail-closed 400 closed the N1-R fixation path but let a sibling subdomain plant the alias on the parent domain and deny service to the whole browser until its cookies were cleared. Honouring only the byte-exact name closes fixation without that availability regression; a genuinely ambiguous duplicate session cookie is still refused (#53).
- CORS no longer reflects arbitrary request origins; cross-origin access requires an explicit allowlist via the `ANNOTATER_CORS_ORIGINS` environment variable (default: none). A bare `*` entry is rejected because, with credentialed CORS, it would reflect every request origin (final-gate finding N6).

## [0.1.0-rc3] - 2026-10-16

> The `0.1.0-rc3` image was published on 2026-10-03; the `v0.1.0-rc3` tag
> and GitHub Release followed on 2026-10-16. This is a pre-release, not the
> final `v0.1.0` release.

### Added
- Assembly-aware chromosome normalization: identifiers are resolved against the selected assembly's bundled registry and renamed only to a verified target name. Unknown identifiers and sequences without a verified target alias are reported and kept as provided, never guessed; coordinates are unchanged.
- 64 genome assemblies across 46 species are bundled offline from pinned UCSC PASS registries, so chromosome normalization needs no runtime network access.
- Custom chromosome mappings as a runtime registry. A mapping is structurally validated without repair, scoped to the workflow or session that supplied it, and never persisted or shared between sessions.
- Normalization of every VCF `##contig` declaration through the selected registry, including contigs that no row uses. Declarations that resolve to the same identifier merge only when their remaining attributes are equivalent; otherwise export fails explicitly.
- Chromosome-registry audit tooling, an upstream-data oracle, parity coverage, and executable semantic examples.

### Changed
- The Streamlit interface uses the bundled assembly catalog for genome-assembly and chromosome-naming selection, and offers custom chromosome mappings for assemblies outside the bundle.
- The obsolete `ChromosomeMapper` path and unused chromosome-style settings were retired, and the chromosome-normalization documentation was rewritten for the assembly-aware model.

### Fixed
- VCF `##contig` identifier parsing is quote-aware, malformed contig declarations are handled tolerantly, and text uploads are byte-limited.
- Registry loading rejects all Unicode control characters, renders chromosome identifiers literally, bounds mapping-error messages, and keeps loaded registries immutable.

## [0.1.0-rc2] - 2026-10-02

### Added
- Assembly-aware chromosome normalization architecture supporting standard assemblies (GRCh38, GRCh37, GRCm39, etc.) and custom coordinate registries.
- Strict parity verification harness between Bedtools and Polars-Bio backends across overlap, closest, and strand-aware modes.
- End-to-end container health smoke checks and deterministic benchmark harness in CI.
- Comprehensive documentation covering deployment, architecture, engine contracts, and reproducibility.

### Changed
- Streamlit application unified backend selection allowing dynamic engine switching with guaranteed schema parity.
- License formalized as BSD-3-Clause across codebase, packaging, and metadata.
